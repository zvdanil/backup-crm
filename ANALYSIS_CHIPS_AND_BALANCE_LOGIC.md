# Аналіз: чіпи остатків і логіка розрахунку для різних рахунків

## 1. Чому немає чіпа для ТОВ «Освітній простір Ірис» (борг 2520)

### Два джерела даних

**Чіпи в «Історія оплат»** беруться з `useAccountOpeningBalancesForMonth`:
- фільтр: `balance_date` = **1-е число обраного місяця** (точна збіжність)
- показують лише записи з `account_opening_balances`, внесені **саме на обраний місяць**

**Блок «Баланс по рахунках»** використовує `useAccountOpeningBalancesCumulativeUpToMonth`:
- фільтр: `balance_date <=` 1-е число місяця
- враховує всі внесені залишки (поточний і попередні місяці)
- також використовує `basePreviousBalance` з API (борг/переплата з попередніх періодів)

### Як це пояснює відсутність чіпа

**Варіант A.** Борг 2520 ₴ для Iris — це **перенесений борг** (з попередніх місяців), без записи в `account_opening_balances` для січня.  
→ Чіп не показується, бо для січня немає явного залишку.

**Варіант B.** Борг 2520 ₴ внесений як залишок у **грудні** (на 01.12.2025).  
→ Він враховується в «Борг на початок» січня через cumulative.  
→ Але чіпи в січні беруться тільки з `balance_date = 2026-01-01`, тому грудневий запис у чіпах не показується.

### Висновок

Чіпи показують лише **залишки, внесені на обраний місяць**.  
Борг/переплата з попередніх місяців (в тому числі з `account_opening_balances`) у чіпах не відображаються, тож користувач не бачить, що борг 2520 фактично «внесений» (наприклад, у грудні).

---

## 2. Чіпи не замінюють один одного

Логіка рендеру чіпів:

```tsx
{balancesForMonth.map((b) => (
  <div key={b.id}>...</div>
))}
```

Відображаються **усі** записи з `balancesForMonth`. Для кожного запису — окремий чіп. Один чіп не замінює інший.

Якщо для Iris немає чіпа, а для ФОП Зверева є, це означає, що для Iris **немає запису** в `account_opening_balances` з `balance_date = 2026-01-01`.

## 3. Поточний баланс 800 ₴ для ФОП Зверева (а не 3200 ₴)

### Вхідні дані

- Переплата на початок: **+1700 ₴**
- До сплати на початок: **700 ₴** (2400 − 1700)
- Оплачено: **700 ₴**
- Всього нараховано в місяці: **3200 ₴** (800 + 2400)

### Формула в коді

```
effectiveStartBalance = 1700  (переплата)
monthlyDelta = payments − charges + refunds = 700 − 3200 = −2500
endBalance = 1700 + (−2500) = −800  → показуємо «До сплати: 800 ₴»
```

### Інтерпретація

- На початок місяця: переплата **1700 ₴**.
- У січні: нарахування **3200 ₴**, оплата **700 ₴**.
- Доступні кошти: 1700 + 700 = **2400 ₴**.
- Сума нарахувань: **3200 ₴**.
- Різниця: 3200 − 2400 = **800 ₴** — це й є борг.

Тобто 800 ₴ — це **результат роботи поточної формули**, а не помилка.

### Чому може очікуватися 3200 ₴

Якщо розглядати окремо:

- До сплати на початок: 700 ₴  
- Оплата 700 ₴ повністю його покриває → борг 0.  
- Нові нарахування: 3200 ₴  
→ логічно очікувати борг 3200 ₴.

Код же застосовує оплату 700 ₴ до **всього** балансу разом із переплатою 1700 ₴:

- старт: 1700 кредит  
- зміна за місяць: 700 − 3200 = −2500  
- підсумок: 1700 − 2500 = −800

Тобто оплата 700 ₴ зменшує нові нарахування, а не лише «До сплати на початок».

### Висновок

Питання не в тому, що рахунки рахуються по-різному, а в тому, **як саме застосовується оплата**:

1. Спочатку до «До сплати на початок», решта до нових нарахувань — тоді борг 3200 ₴.  
2. Оплата застосовується до загального балансу разом із переплатою — тоді борг 800 ₴ (як зараз).

## 4. Порівняння логіки для Iris і ФОП Зверева

| Параметр            | Iris                          | ФОП Зверева                     |
|---------------------|-------------------------------|----------------------------------|
| Чіп у історії       | немає                         | є (+1700)                        |
| Джерело боргу/переплати | API + cumulative              | явний залишок у січні            |
| Тип активностей     | садок (subscription)          | додаткові заняття (recalculation)|
| Формула балансу     | та сама                       | та сама                          |

Різниця лише в тому, звідки береться `displayPreviousBalance` і `effectiveStartBalance` (API vs `account_opening_balances`). Сама формула `endBalance = effectiveStartBalance + monthlyDelta` однакова.

## 5. Що можна змінити

1. **Чіпи**  
   Показувати не лише залишки, внесені на обраний місяць, а й ті, що впливають на «Борг/Переплата на початок» (наприклад, через cumulative або окремий механізм).

2. **800 vs 3200**  
   Якщо потрібна поведінка «оплата спочатку покриває борг на початок, потім — нові нарахування», потрібно змінити логіку застосування платежу в розрахунку поточного балансу.
