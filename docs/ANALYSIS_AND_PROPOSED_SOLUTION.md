## 3. Где была применена неверная логика

### 3.1. previous_balance (главная ошибка)

- **Сделано:** для некумулятивного режима пытались считать «остаток на начало» только по транзакциям: сумма по `account_id` (payment +, income −, expense +), без учёта начислений по подпискам и посещаемости.
- **Почему неверно:** фактический баланс на начало месяца = конец предыдущего месяца, а он считается как payments − charges + refunds, где charges включают и подписки, и посещаемость. Упрощение «только транзакции» даёт другую формулу и ломает согласованность с отображаемым балансом и привязкой к счетам.
- **Следствие:** расхождение «Баланс на початок» с реальностью и возможное искажение по счетам привязки.

### 3.2. Сокращение периода расчёта для некумулятивного режима

- **Сделано:** для одного месяца считали только этот месяц (`monthsToCalculate = [{ month, year }]`), а previous_balance — из упрощённой агрегации транзакций за предыдущие месяцы.
- **Почему неверно:** корректный previous_balance должен быть суммой помесячных балансов за все предыдущие месяцы, по той же формуле (в т.ч. подписки и посещаемость). Иначе привязка к счетам и итоговые цифры не совпадают с «правильным» старым вариантом.

### 3.3. Разделение источников данных для «Нараховано за місяць»

- **Сделано:** в UI отдельно подгружалась история цен и считался `subscriptionChargesByAccount`; в одном из вариантов в карточке счета показывали именно его вместо `accountBalance.charges`.
- **Почему рискованно:**  
  - «Нараховано за місяць» должно совпадать с тем, что участвует в балансе (payments − charges + refunds), иначе пользователь видит одно число, а баланс считается от другого.  
  - Если нужна именно «только подписная часть» — она должна считаться по той же логике, что и в расчёте баланса (те же цены, те же даты), а не отдельным запросом в UI.  
  - Дополнительный запрос истории в UI добавляет задержку («сначала окно, потом активности»).

### 3.4. Привязка к счетам (account_id)

- **Что могло сломаться:**  
  - Упрощённый расчёт previous_balance шёл только по `trans.account_id`; при этом в основном расчёте счёт определяется как `enrollment.account_id ?? activity.account_id`. Транзакции без activity_id (оплаты «без активности») уже привязаны к account_id; для income/expense привязка к счету активности могла учитываться иначе. Итог — разная группировка по счетам в previous_balance и в основном балансе.  
  - Любое изменение, которое уменьшало использование `enrollmentData.account_id ?? activityAccountMap[activity_id]` в расчёте или подменяло источник данных (например, только транзакции), могло привести к тому, что «данные по счетам привязки перестали учитываться».

### 3.5. Фильтр по enrolled_at в computeStudentAccountBalancesFromData

- В текущем (восстановленном) коде фильтр по месяцу в хуке не использует `enrolled_at` / `unenrolled_at`, только `is_active` и дату отписки в этом месяце.
- Добавление фильтра `enrolled_at <= monthEnd` и `unenrolled_at >= monthStart` в цикле по месяцам — правильное направление, но его нужно вводить аккуратно, не трогая формулу баланса и разрешение account_id.

## 4. Принципы, которых придерживаться

1. **Один источник истины для баланса**  
   Все числа в карточке счёта (в т.ч. «Нараховано за місяць») должны браться из результата расчёта баланса (хук), а не из отдельно посчитанного в UI «только подписки».

2. **previous_balance не упрощать**  
   Считать как сумму помесячных балансов за все предыдущие месяцы по той же формуле, что и для текущего месяца (с теми же правилами по подпискам, посещаемости и account_id).

3. **Единое правило по счетам**  
   Везде: account_id = `enrollment.account_id ?? activity.account_id` (и в расчёте по активностям, и при агрегации транзакций/остатков). Не вводить расчёт «только по transaction.account_id» для части формул.

4. **История цен — внутри расчёта баланса**  
   Если нужна история цен подписок для корректных начислений по датам — загружать её там же, где считаем баланс (в хуке), и передавать в `computeStudentAccountBalancesFromData` / `calculateMonthlyBalanceFromData`. Не делать отдельный запрос в UI для «Нараховано за місяць».

5. **Сначала корректность, потом скорость**  
   Не менять формулы и период расчёта ради скорости; оптимизировать только параллельными запросами, кэшем или выносом в БД без изменения логики.

## 5. Предлагаемое решение (по шагам, для согласования)

### Шаг 1. Фильтр по датам подписки (без смены формул и счетов)

- **Где:** в `useFinanceTransactions.ts` в цикле по месяцам при формировании `filteredEnrollments`:  
  - не включать enrollment, если `enrolled_at > monthEnd`;  
  - не включать, если `unenrolled_at < monthStart`.  
- **Не менять:** формулу баланса, разрешение account_id, период загрузки данных (как сейчас — от первого enrolled_at до endDate).
- **Цель:** в январе не показывать начисления по активности, на которую записались только в феврале; окно балансов и привязка к счетам остаются как в текущем коде.

### Шаг 2. История цен подписок (таблица + использование в расчёте)

- Оставить миграцию `enrollment_price_history` и логику в `useEnrollments` (создание записи при смене цены).
- В `fetchStudentAccountBalances`:  
  - загружать `enrollment_price_history` для нужных enrollment_id в том же батче запросов (параллельно с transactions, attendance, activities);  
  - передавать `enrollmentPriceHistoryMap` в `computeStudentAccountBalancesFromData` и использовать в `calculateMonthlyBalanceFromData` для получения цены на дату (например, через `getEnrollmentPriceForDate`).
- Не загружать историю цен подписок отдельно в `StudentAccountBalance.tsx` для расчёта «Нараховано за місяць».

### Шаг 3. UI: один источник данных, окно всегда видно

- «Нараховано за місяць» в карточке счёта — всегда из `accountBalance.charges` (результат хука), а не из отдельного `subscriptionChargesByAccount`.
- Окно балансов не скрывать при отсутствии активностей в месяце: не делать `if (balanceEnrollments.length === 0) return null`; показывать блок по счетам с нулями/пустым списком активностей.
- Группировка по счетам в UI оставить как сейчас: по `enrollment.account_id || enrollment.activities.account_id || "none"`, чтобы совпадала с группировкой в хуке.

### Шаг 4. Оптимизация только без смены логики

- Параллелить запросы в `fetchStudentAccountBalances`: например, один Promise.all для (V1 base tariff ids, enrollments), второй — для (transactions, attendance, activities, при необходимости enrollment_price_history).
- Не сокращать период загрузки транзакций/attendance и не упрощать формулу previous_balance.
- При желании позже — вынести расчёт балансов в БД (RPC/view) с точным повторением текущей формулы; фронт тогда только вызывает RPC и отображает.

### Шаг 5. Диалог истории цены подписки (по желанию)

- Кнопка «История» в карточке подписки и `EnrollmentPriceHistoryDialog` можно вернуть; они не влияют на расчёт баланса и привязку к счетам.

## 6. Чего не делать

- Не считать previous_balance только по транзакциям (без подписок и посещаемости).
- Не уменьшать `monthsToCalculate` для некумулятивного режима так, чтобы previous_balance считался по другой формуле.
- Не показывать «Нараховано за місяць» из отдельного запроса/расчёта в UI; не подменять `accountBalance.charges` на `subscriptionChargesByAccount` в этой ячейке.
- Не менять правило разрешения счёта: везде использовать `enrollment.account_id ?? activity.account_id` (и не переходить на один только `transaction.account_id` для части расчётов).
- Не вводить рефакторинг с дублированием блоков (balanceEnrollments, useQuery и т.д.), чтобы избежать синтаксических ошибок и расхождений логики.
