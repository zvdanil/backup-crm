# Итоговое видение модернизации

## 1. Цели

- Корректные отчёты и балансы: начисления, оплаты, остатки, привязка к счетам, «Прогноз доходу» = charges − refunds.
- Историческая корректность: в месяце показывать только то, что реально действовало (подписки по датам, цены по периодам).
- Один источник истины для всех цифр в UI; без дублирования логики и лишних запросов в компонентах.
- Скорость — только за счёт параллельных запросов и кэша, без упрощения формул расчёта.

---

## 2. Два типа тарифов и «история»

### 2.1. Фактические тарифы (по посещениям)

- Начисления считаются по факту посещений (журналы посещений).
- **История начислений** уже есть в журнале: при каждой отметке фиксируется действующая на ту дату цена/сумма (например, `charged_amount`). Смена цены в тарифе не переписывает прошлое — новые посещения идут по новой цене.
- **Отдельная таблица истории цен для расчётов не нужна.** Всё необходимое для истории начислений — в журнале посещений.

**Модернизация для этого типа:** не вводить лишнюю «историю цен»; при расчётах использовать только транзакции и посещения (как сейчас). При необходимости — только уточнить фильтрацию по датам (подписка действовала в этом месяце).

### 2.2. Абонплатные тарифы (подписка за период)

- Начисление за месяц — фиксированная сумма за период (абонплата).
- **Историю цен храним статично:** при смене цены подписки (или тарифа) создаётся запись с ценой/скидкой и **периодом действия** (например, `effective_from`, `effective_to`).
- **При расчёте за конкретный месяц:** по датам периодов действия выбираем, какая запись истории действовала в этом месяце, и берём из неё цену для начисления.

**Модернизация для этого типа:**
- Таблица истории цен с периодами действия (например, `enrollment_price_history`: `enrollment_id`, `custom_price`, `discount_percent`, `effective_from`, `effective_to`).
- При изменении цены подписки — создание новой записи в истории и закрытие предыдущей (`effective_to` = дата смены).
- В расчёте баланса за месяц: для абонплатных активностей не брать только текущие `enrollment.custom_price` / `activity.billing_rules`, а определять цену по дате месяца и периодам из истории; если истории нет — fallback на текущие значения.

---

## 3. Расчёт балансов (общие принципы)

- **Один контур расчёта** в хуке: загружаем все нужные данные (enrollments, transactions, attendance, activities, при абонплате — история цен подписок), считаем помесячно, получаем по каждому счёту: `balance`, `payments`, `charges`, `refunds`, `previous_balance`, и т.д.
- **Привязка к счетам везде одинаковая:** `account_id = enrollment.account_id ?? activity.account_id`. Никакой отдельной агрегации «только по transaction.account_id» для части формул.
- **previous_balance:** сумма помесячных балансов за все предыдущие месяцы по той же формуле (подписки + посещаемость + те же правила по счетам). Не упрощать до «только транзакции».
- **Период загрузки данных:** от самой ранней даты подписки до конца выбранного месяца (как в текущем рабочем варианте), чтобы корректно считать все месяцы и previous_balance.

---

## 4. Фильтрация по датам подписки

- В расчёте по каждому месяцу в цикле: enrollment учитывается только если:
  - `enrolled_at <= конец месяца`;
  - `unenrolled_at` отсутствует или `unenrolled_at >= начало месяца`.
- Итог: в январе нет начислений по активности, на которую записались в феврале; отписанные в прошлом месяце не тянут начисления в текущем. Логика единая для фактических и абонплатных тарифов.

---

## 5. UI

- **Окно балансов по счетам** всегда отображается (даже если в месяце нет активностей — пустой список и нули по счетам).
- **Все числа в карточке счёта** (баланс на початок, нараховано за місяць, оплачено, поточний баланс) берутся **только из результата хука** (`accountBalance`), без дублирующего расчёта в компоненте.
- **Группировка по счетам** в UI совпадает с расчётом: `enrollment.account_id || activity.account_id || "none"`.
- **История цен подписок** не подгружается отдельным запросом в компоненте — только внутри хука, для расчёта; при желании в карточке подписки можно показывать диалог «История изменения цены» по уже загруженным или отдельно запрошенным данным только для отображения, без участия в формулах баланса.

---

## 6. Производительность

- Параллельные запросы в `fetchStudentAccountBalances`: один батч (например, V1 base tariff ids + enrollments), второй (transactions + attendance + activities + при необходимости enrollment_price_history для нужных enrollment_id).
- Не сокращать период загрузки и не менять формулу previous_balance ради скорости.
- Дальнейшее ускорение (при необходимости) — вынос расчёта в БД (RPC/view) с точным повторением той же логики; фронт только вызывает и отображает.

---

## 7. Итоговая схема по типам тарифов

| Тип тарифа           | Где «история»                     | Что делаем при модернизации                                      |
|----------------------|-----------------------------------|-------------------------------------------------------------------|
| Фактический (посещения) | Журнал посещений (цена на дату)   | Не вводим таблицу истории цен; расчёт по журналу и транзакциям   |
| Абонплатный (подписка)  | Таблица истории с периодами       | Храним периоды действия цен; в расчёте за месяц берём цену по дате периода |

Единые для обоих: фильтр по датам подписки, один источник истины в UI, единое правило по счетам, корректный previous_balance.

---

## 8. Порядок внедрения

1. **Фильтр по датам подписки** в расчёте по месяцам (без смены формул и таблиц).
2. **История цен для абонплаты:** таблица с периодами, создание записей при смене цены, использование периодов в расчёте начислений за месяц.
3. **UI:** один источник данных, окно балансов всегда, «Нараховано за місяць» из `accountBalance.charges`.
4. **Оптимизация:** параллельные запросы и при необходимости кэш или RPC без изменения логики.

После этого система соответствует описанному видению: история начислений для фактических тарифов — в журнале; для абонплаты — статичная история цен с учётом периодов действия при расчётах.
