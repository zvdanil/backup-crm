# Контракт модернизации выплат ЗП (Шаг 1)

## Статус

- Документ фиксирует неизменяемые правила перед реализацией рефакторинга.
- Любой следующий шаг должен проверяться на соответствие этому контракту.

## Эталон (Source of Truth)

- Эталон отображения выплат ЗП: календарная сетка в разделе `Фінансова історія` (по педагогам).
- После модернизации поведение и цифры в этой сетке должны остаться такими же, как до начала работ.

## Каноничная модель данных

- Каноничный источник выплат ЗП: `staff_payouts`.
- `finance_transactions` с `type='salary'` — производная запись для финансового учета (расходы, отчеты, комиссии, аналитика).

## Единый UI попап выплаты

- Используется единый попап из финансовой истории для всех точек внесения выплат ЗП.
- Поля:
  - `Сотрудник` — обязательно всегда.
  - `Подкатегория` — необязательно.
  - `Дата выплаты` — редактируемая.
  - Остальные поля сохраняются по текущей логике попапа (счет, комментарий, комиссия и т.д.).

## Правила предзаполнения сотрудника

- Из финансовой истории: сотрудник предзаполняется (контекст карточки педагога).
- Из журнала затрат (строка выплат): сотрудник предзаполняется (контекст строки педагога).
- Из журнала зарплаты: предзаполнения нет, выбор обязателен вручную.

## Сквозное отображение выплат

- Выплаты, внесенные из любого источника (фин. история, журнал затрат, журнал зарплаты), должны:
  - отображаться в финансовой истории;
  - отображаться в журнале затрат `Зарплата`;
  - не дублироваться.
- В UI выплат показываются только фактически введенные значения выплаты (из `staff_payouts`), без merge-логики с `finance_transactions` как отдельного источника отображения.

## CRUD и согласованность

- Create: создается каноничная выплата в `staff_payouts` и связанная производная `finance_transactions(type='salary')`.
- Update: выплата и связанная salary-транзакция обновляются атомарно в одном сценарии.
- Delete: только soft delete, причина удаления обязательна.
- Удаленные записи скрыты в обычных экранах; в будущем может быть отдельный журнал удалений.

## Комиссия

- Комиссия остается отдельной логикой, привязанной к salary-транзакции.
- При создании и редактировании выплаты синхронизация комиссии сохраняется.

## Поведение по датам и множественным выплатам

- При изменении даты выплата исчезает из старой ячейки и появляется в новой во всех экранах.
- Разрешены несколько отдельных выплат одному сотруднику в один день.
- Такие выплаты должны отображаться отдельными записями (не схлопывать в одну).

## Backfill старых данных

- Выполняется backfill недостающих связей `staff_payouts <-> finance_transactions` и данных подкатегории.
- Неоднозначные случаи не автоправятся и попадают в техотчет на ручную проверку.

## Границы релиза

- В рамках текущего рефакторинга: унификация попапа и единый сквозной поток выплат ЗП (create/update/delete/display).
- Новые дополнительные фичи интерфейса (кроме требуемой унификации и обязательных полей) не входят в релиз.
